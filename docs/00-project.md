# Personal Skin Care

## Происхождение

Собственный проект команды. Ранее вёлся в четырёх репозиториях и перенесён в текущий репозиторий через git subtree.

## Назначение и проблема

Веб-платформа на базе ИИ для подбора индивидуального ухода за кожей лица. С помощью компьютерного зрения система анализирует фотографии, определяет тип и состояние кожи, формирует персональные рекомендации и позволяет вести историю анализов для мониторинга динамики.

Проблема заключается в разрыве между растущим спросом на персонализированный уход и отсутствием объективных инструментов самодиагностики. Пользователи вынуждены подбирать косметику методом проб и ошибок, ориентируясь на противоречивые советы из интернета или универсальные предложения магазинов.

## Пользователи и роли

Целевые пользователи - молодые люди 18-35 лет, которые предпочитают онлайн-покупки и самостоятельный подбор косметики, но не имеют возможности регулярно посещать косметолога.

Роль: пользователь. Доступны регистрация, вход, профиль, загрузка фотографий, просмотр результатов и истории анализов.

Внешняя система: ML-сервис определения типа кожи.

## Три основные функции

1. Регистрация, вход и управление профилем.
2. Загрузка фотографии и анализ типа кожи ML-сервисом.
3. Просмотр результата с рекомендациями и истории анализов.

## Технологический стек

- Backend: Go 1.25, Gin, GORM, PostgreSQL 17, MinIO, JWT, Swagger.
- ML: Python 3.11, FastAPI, PyTorch 2.3.1, timm, EfficientNet-B2, OpenCV.
- Frontend: React 19, TypeScript 5.9, Vite 8, Tailwind CSS 4, React Router 7, Axios.
- Инфраструктура: Docker, Docker Compose.

## Структура проекта

### Компоненты и каталоги

Personal Skin Care — веб-приложение из трёх основных компонентов: фронтенда на React/TypeScript, бэкенда на Go/Gin и ML-сервиса на Python/FastAPI. Взаимодействие компонентов и инфраструктурных сервисов настроено через `src/docker-compose.yml`.

**Фронтенд (`src/frontend/`).** Точка входа — `src/main.tsx`, маршрутизация — `src/App.tsx`. Страницы находятся в `src/pages/`: регистрация, вход, загрузка фотографии, результат, история и настройки. Папка `src/shared/api/` содержит HTTP-клиент и запросы к API, `src/shared/ui/` и `src/shared/layout/` — общие элементы интерфейса, `src/mocks/` — демонстрационные данные.

**Бэкенд (`src/backend/`).** Точка входа — `cmd/server/main.go`. В `internal/app/` находятся запуск приложения, зависимости и HTTP-маршруты. Папка `internal/handler/` обрабатывает запросы, `internal/service/` реализует бизнес-логику, `internal/repository/` и `internal/db/` отвечают за доступ к PostgreSQL. В `internal/integration/ml/` находится клиент ML-сервиса, в `internal/security/` и `internal/middleware/` — авторизация и промежуточные обработчики, а в `internal/config/` — загрузка настроек. Миграции базы данных находятся в `migrations/`, начальные данные — в `scripts/seeds.sql`.

**ML-сервис (`src/ml-service/`).** Основной файл — `src/app.py`: FastAPI-приложение загружает EfficientNet-B2, обрабатывает фотографии и предоставляет метод `/predict`. Веса модели должны находиться в `models/` и скачиваются отдельно.

**Инфраструктура и документация.** `src/docker-compose.yml` описывает запуск компонентов и инфраструктурных сервисов. `README.md` содержит инструкцию запуска, `docs/` — документацию проекта, `CHANGELOG.md` — журнал изменений, `tests/` предназначен для тестов.

### Взаимодействие сервисов

Пользователь работает во фронтенде (порт `5173`). Фронтенд отправляет запросы к API бэкенда (порт `8080`); в Docker-конфигурации Vite использует прокси на `backend:8080`. Бэкенд хранит структурированные данные в PostgreSQL (порт `5432`), а фотографии — в MinIO (порты `9000` и `9001`). Для определения типа кожи бэкенд обращается к ML-сервису (порт `8000`) по HTTP. ML-сервис использует загружаемую при старте модель EfficientNet-B2 и возвращает тип кожи, уверенность модели и вероятности классов.

При загрузке фотографии бэкенд проверяет расширение (`.jpg`, `.jpeg`, `.png`), сохраняет файл и запись анализа, а затем асинхронно вызывает ML-сервис. Анализ проходит состояния `processing`, `completed` или `failed`. Рекомендации и подходящие ингредиенты выбираются бэкендом из данных PostgreSQL для определённого типа кожи.

В Docker Compose также есть одноразовые сервисы `migrate` (применение миграций) и `seed` (начальные данные). PostgreSQL и MinIO используют именованные тома `postgres_data` и `minio_data` для сохранения данных после перезапуска контейнеров.

### Настройки и внешние зависимости

Общий шаблон конфигурации — `src/.env.example`; рабочий `src/.env` создаётся локально и не должен содержаться в репозитории. Настройки бэкенда считываются из переменных окружения в `internal/config/config.go`: `POSTGRES_*` для БД, `MINIO_*` для файлового хранилища, `JWT_*` для токенов и `ML_*` для взаимодействия с ML. Для фронтенда предусмотрены `VITE_API_URL`, `VITE_USE_MOCK_ANALYSIS` и `VITE_PROXY_TARGET`. Для ML используются `MODEL_PATH`, `MODEL_VERSION`, `API_KEY`. Основные зависимости описаны в `src/frontend/package.json`, `src/backend/go.mod` и `src/ml-service/requirements.txt`.

Примечание: в проверенной ветке отсутствует каталог `src/backend/internal/integration/storage/`, хотя он импортируется исходниками бэкенда. Сборка Go действительно завершается ошибкой отсутствующих пакетов; требуется отдельное issue. Веса ML-модели тоже не включены в Git, но их отдельная загрузка прямо предусмотрена README — само по себе это не дефект.

## Карта функций

### Регистрация и вход

**Регистрация.** Реализация: `src/frontend/src/pages/RegisterPage.tsx`, `src/frontend/src/shared/api/authApi.ts`, `src/backend/internal/handler/auth.go`, `src/backend/internal/service/auth.go`. Проверка: открыть `/register`, заполнить форму и убедиться, что регистрация выполняется либо появляется понятное сообщение об ошибке.

**Вход.** Реализация: `pages/LoginPage.tsx`, `shared/api/authApi.ts`, `handler/auth.go`, `service/auth.go`. Проверка: открыть `/login`, ввести данные зарегистрированного пользователя и проверить доступ к защищённым страницам.

**Выход и защита страниц.** Реализация: `shared/api/authApi.ts`, `authStorage.ts`, `app/RequireAuth.tsx`, `handler/auth.go`. Проверка: войти, выйти из аккаунта и убедиться, что защищённые страницы снова требуют авторизацию.

### Профиль пользователя

**Просмотр профиля.** Реализация: `pages/SettingsPage.tsx`, `shared/api/userApi.ts`, `handler/user.go`, `service/user.go`. Проверка: после входа открыть `/settings` и посмотреть данные пользователя.

**Редактирование профиля.** Реализация: те же файлы страницы настроек и API пользователя. Проверка: изменить доступные поля, сохранить изменения и обновить страницу.

**Смена пароля.** Реализация API: `handler/user.go`, маршрут `PATCH /users/me/password`. В `pages/SettingsPage.tsx` есть элементы интерфейса, но оставлена пометка TODO о поле `current_password`. Проверка: отдельно выяснить, работает ли полный сценарий смены пароля через интерфейс; при необходимости проверить API.

**Удаление аккаунта.** Реализация API: `handler/user.go`, маршрут `DELETE /users/me`. Проверка: выяснить, предусмотрена ли кнопка в интерфейсе; при её отсутствии проверять API только на тестовом аккаунте.

### Анализ кожи

**Загрузка фотографии и создание анализа.** Реализация: `pages/UploadPage.tsx`, `shared/api/analysisApi.ts`, `handler/analysis.go`, `service/analysis.go`. Проверка: на `/upload` выбрать JPG или PNG с лицом, отправить файл и проверить переход к результату либо отображение обработки.

**Определение типа кожи.** Реализация: `src/ml-service/src/app.py`, `backend/internal/integration/ml/client_http.go`, `service/analysis.go`. Проверка: при работающих сервисах загрузить фотографию и проверить появление типа кожи.

**Результат и рекомендации.** Реализация: `pages/ResultPage.tsx`, `shared/api/analysisApi.ts`, `service/analysis.go` и репозитории рекомендаций. Проверка: открыть `/result/:id` после завершения анализа, проверить тип кожи и рекомендации.

**История анализов.** Реализация: `pages/HistoryPage.tsx`, `shared/api/analysisApi.ts`, `handler/analysis.go`, `service/analysis.go`. Проверка: открыть `/history`, убедиться в наличии предыдущих анализов и возможности перейти к подробностям.

**Удаление анализа.** Реализация: `pages/HistoryPage.tsx`, `shared/api/analysisApi.ts`, `handler/analysis.go`, `service/analysis.go`. Проверка: удалить тестовую запись, обновить историю и проверить, что запись исчезла; отдельно проверить поведение в mock-режиме.

**Оговорка:** таблица составлена по исходным файлам и зарегистрированным маршрутам API; успешное сквозное выполнение этих сценариев пока не подтверждено запуском приложения.

## Состояние практик

**Контроль версий — есть.** Используется Git, совместная работа ведётся в GitHub; для лабораторной создана ветка `lab-1`.

**Инструкция по запуску — есть.** В корневом `README.md` и README компонентов описаны запуск через Docker Compose и ручная проверка приложения.

**Документация API — есть.** Используется Swagger (`src/backend/docs/swagger.yaml`, `swagger.json`), предусмотрен маршрут `/swagger/*any`.

**Линтер — частично.** Для фронтенда настроен ESLint, команда запуска: `cd src/frontend && npm run lint`. Настроек линтеров Go и Python в просмотренных файлах не обнаружено.

**Проверка сборки — частично.** Для фронтенда есть команда `cd src/frontend && npm run build`, запускающая TypeScript и Vite. Общая сборка предусмотрена через Docker Compose. Отдельная проверка `cd src/backend && go build ./cmd/server` на macOS с Go 1.25.0 завершилась ошибкой из-за отсутствующих пакетов `storage` и `storage/minio`.

**Автоматические тесты — не обнаружены.** Поиск файлов `*_test.go`, `test_*.py`, `*.test.ts(x)` и `*.spec.ts(x)` результатов не дал. Каталог `tests/` не содержит тестов, а в `package.json` фронтенда нет скрипта `test`.

**CI/CD — не обнаружено.** В проверенной ветке нет `.github/workflows/` и `.gitlab-ci.yml`. Автоматические проверки при создании pull request не подтверждены.

**Документация архитектурных решений — нет содержимого.** В `docs/adr/` находится только `.gitkeep`.

**Диаграммы — нет содержимого.** В `docs/diagrams/` находится только `.gitkeep`.

**Журнал изменений — формально есть.** Файл `CHANGELOG.md` существует, но пуст.

**Контейнеризация — есть.** Для компонентов предусмотрены Dockerfile, общий `src/docker-compose.yml`, а также отдельные шаги миграции и заполнения базы данных.
